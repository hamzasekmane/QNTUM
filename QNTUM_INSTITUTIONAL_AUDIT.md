# QNTUM institutional engineering audit — Phase 1

## Scope and limits
Read-only audit of current source on `arena/f6fb8d86-qntum`, with source-path traces for recovery, scanner validity, and execution; review of composition root and module boundaries; available Python/static tests executed. User's prompt's raw-log slot contained only a placeholder. Earlier conversation supplied 11:58 and 12:04 runtime excerpts and is treated as observational evidence, not reproducible terminal evidence. No MetaEditor/MT5, no user Common Files state, no EX5 binary, broker statement, or live account access. This is not a compile, backtest, broker reconciliation, or production approval.

## Executive findings
1. **Recovery is fail-closed as designed, not currently resolved.** Legacy unscoped `qme_state.txt` plus absent scoped checkpoint sets recovery block; Engine reports FAULT and blocks entries/checkpoint writes. `starting clean` refers only to absent scoped file. The legacy state cannot safely be ignored without reconciliation. See QNTUM_ROOT_CAUSE_REPORT QME-AUD-01.
2. **Recovery parser is not transactional.** It applies sections in order and can discover invalid intent records after earlier stores have already changed. The engine remains blocked, but in-memory partial restore can confuse diagnostics/recovery. QME-AUD-03.
3. **Runtime path naming discrepancy needs build provenance.** Supplied log name does not match current source path function format. No conclusion about which file the running binary actually used until EX5 and terminal Common Files are identified. QME-AUD-04.
4. **Scanner diagnostics conflate semantics.** `lastAnalysed` and `lastDataValid` are assigned the same count; `valid` is recomputed from current snapshots. `tfReady` is a multi-stage success flag, not raw data readiness. QME-AUD-05/06.
5. **Broker API ownership is duplicated for management operations.** OrderManager's claim that it is the sole OrderSend site conflicts with direct TradeManager sends for protection/close. Static evidence does not show an unguarded new-entry bypass. QME-AUD-08.

## Lifecycle, runtime, execution, and monitoring observations
- Entry lifecycle in main: MT5 init -> build config -> Engine initialize -> timer; tick/timer invokes Engine; trade transaction forwards broker transaction; deinit calls Engine shutdown and releases output/monitoring. (See `QME_Main.mq5` around OnInit/OnDeinit/OnTick/OnTimer/OnTradeTransaction; exact source lines available via `nl -ba QME_Main.mq5`.)
- A symbol context can fail initialization independently inside Scanner's symbol loop; whether all symbols are discarded depends on scanner initialization logic. At scan time per-symbol refresh failures do not necessarily fail the whole scanner: completed refresh returns true even if zero symbols valid (`Runtime/Scanner.mqh:298-321`). Account refresh failure faults whole Engine (`Runtime/Engine.mqh:735-745`).
- `lastAnalysed` and `lastDataValid` counts are both incremented only for `snapshot.dataValid` at the current source lines 301-316. `valid` summary counts snapshots dynamically at lines 593-606. They do not represent independent counts.
- `tfReady[i]` is cleared before refresh and only set after context, indicators, series and analysis succeed (`Scanner.mqh:324-348`). Snapshot data validity further requires quality on every TF and a fresh tick (`399-423`). Thus `ready`, `valid`, `lastDataValid`, health and recovery are distinct concepts.
- Tick freshness uses tick timestamp against `TimeTradeServer()` with future/zero rejection and 300-second limit at `Data/TickProcessor.mqh:140-152`; local processing time is not used.
- New entries: Engine recovery gate allows signal-only scan only when analysis-only true and demo/real/armed all false (`Engine.mqh:748-764`); gateway validates request/risk, claims idempotency, checkpoints before sending, then OrderManager sends. Position protection/close is separate and has direct TradeManager calls.
- `INITIALIZED` status is explicitly not operational/trading-ready in supplied monitoring line. Recovery fault is intentionally preserved; initialization must not be read as healthy.
- Supplied 12:04 log indicates scanner valid=4, scans=1 and signal preview on while recovery remains blocked; no execution was built/sent. This is internally possible: preview scanning is allowed but execution/checkpoint remain disabled. Signal rejections such as NO_CONFLUENCE/NO_STRUCTURE/LOW_SCORE are strategy filters, not recovery failures.
